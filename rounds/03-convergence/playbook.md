# Problem-Convergence Brief Case Study (Team Dua style, Round 3)

This skill produces a 4-page problem-convergence brief in the visual and narrative style of the "Team Dua" working-mothers case study, Round 3. It is the **Define 2.0** / **Converge** / **Opportunity Framing** phase of a service-design project — the deliverable that takes the team from "we mapped a massive problem space" (Round 2's output) to "we have committed to ONE problem area, here is its deep map, here is why it matters, and here are the refined questions that will guide ideation."

It is the third in a paired skill series:
1. `discovery-brief-case-study` (Round 1) — narrow from global to an HMW
2. `empathy-deepening-brief-case-study` (Round 2) — expand the HMW into a full problem ecosystem
3. `problem-convergence-brief-case-study` (Round 3, this skill) — converge to one problem area, justify it, refine into sharper sub-HMWs

The output is a **content + layout specification**. Claude writes the prose, problem scoring rationale, ecosystem map content, pain points list, impact + viability arguments, refined HMW questions, and need statement, and specifies the visual elements needed (radar chart with team-member overlays, multi-layer ecosystem map, painpoints-around-icon visualization, market-data callouts). The user takes that spec into Figma, Canva, InDesign, or similar to produce the final designed PDF.

---

## When to use this skill

Use this skill when the user asks for:

- A Round 3 / Phase 3 / Converge / Define 2.0 case study deliverable
- A problem-scoring or problem-narrowing artifact with multi-criteria scoring
- An ecosystem map of a specific opportunity area (themes + needs + touchpoints + stakeholders + linkages)
- A pain-points-of-existing-service visualization
- An impact + business viability justification for a chosen problem area
- Refined HMW questions that split an original HMW into multiple sub-questions
- A formal Need Statement in User + Need + Insight ("so that") format

**Do not use this skill if Rounds 1 and 2 haven't been done.** The convergence logic of Round 3 only works if there's both a Round 1 HMW (to converge toward) and a Round 2 problem space (to converge from). If the user hasn't completed both, suggest they use the prior skills first.

---

## The core mental model: Converge → Commit → Refine

Round 1 was the **Funnel** — narrowing global context to a sharp HMW question.
Round 2 was the **Expansion** — opening that HMW into a comprehensive problem ecosystem.
Round 3 is the **Converge-Commit-Refine** arc — taking the massive Round 2 problem space and:

1. **Anchor** — re-state the Round 1 HMW prominently (reminds reader of the question being answered)
2. **Score** — quantify candidate problems against shared criteria (Feasibility, Excitement, Scalability, Business Viability, Impact, Sustainability, Interconnectivity)
3. **Eliminate** — name rejected problems with explicit, structured reasoning (scope mismatch / low interconnectivity / specialization required)
4. **Choose** — name the focus problem with positive justification grounded in the prior research
5. **Map deeper** — build a multi-layer ecosystem map of the chosen problem (themes + needs + touchpoints + stakeholders + interlinkages)
6. **Identify pain in the existing system** — pinpoint failure modes of the current solution landscape
7. **Justify socially** — make the impact case across multiple ripple layers
8. **Justify commercially** — make the market case with real data
9. **Refine the question** — split the original HMW into 3 sharper sub-HMWs at different angles
10. **State the need** — formal User + Need + Insight statement

The structural argument the brief makes is: "We had a broad HMW. We mapped a huge problem space. We have evaluated candidate problems against shared criteria. We commit to this one. Here's the deep map of it, here's why it matters socially and commercially, and here's how we've refined our original question."

If your draft doesn't visibly do all ten moves, the round isn't doing its job.

## Continuity with Rounds 1 and 2

Before drafting, verify the following carry over cleanly:

- **The Round 1 HMW is unchanged** (Round 3 may *refine* it into sub-questions, but cannot pivot to a different topic)
- **The target user is the same** as in Rounds 1 and 2
- **The chosen problem area on this round must be visible in Round 2's problem mapping** — if the chosen problem doesn't appear anywhere in Round 2's mind-map, the convergence is incoherent (the team is committing to a problem they hadn't researched)
- **The voice, palette, and visual style** match the prior rounds
- **The team name and members** remain unchanged

Round 3 is the team's continued work, not a new project. If the user wants to pivot the user/topic mid-project, that's an earlier-round redo, not a Round 3.

## Document anatomy (4 pages)

| Page | Sections | Job to be done |
|------|----------|----------------|
| 1 | Introduction + HMW Callout + Problem Scoring + Narrowing Down | Anchor to Round 1 HMW; quantify candidate problems via team scoring; eliminate with reasoning; choose with justification |
| 2 | Ecosystem Map (of the chosen problem area) | Build a multi-layer atlas of the chosen problem — themes, needs, touchpoints, stakeholders, inter-theme linkages |
| 3 | Pain Points + Indian/Regional Scenario (revisited for the chosen problem) + Setbacks of [Existing Service] | Identify failure modes in the existing solution landscape; re-contextualize the chosen problem; deepen the Round 2 services audit with quantified evidence |
| 4 | Impact + Business Viability + How Might We? (refined) + Need Statement | Justify socially + commercially; refine the broad HMW into 3 sharper sub-HMWs; state the formal need |

Section names can be adapted to the problem, but the **functional role** of each section must remain.

## Section-by-section writing playbook

### Page 1, Section 1: Introduction + HMW Callout

**Function:** Re-anchor to the Round 1 HMW after Round 2's expansion. Name the convergence problem the team now faces.

**Length:** A 3–4 sentence opener + the Round 1 HMW in a prominent callout bubble.

**Structure:**
- **Opening paragraph** (3–4 sentences) following this rhythm:
  - Acknowledge what Rounds 1 and 2 surfaced: "Engaging in extensive stakeholder conversations and secondary research during the preliminary stage revealed that the challenges faced by [USER] are diverse and depend on various factors."
  - Name the dimensions of variation: "These include their [LIST 3–5 axes of variation — e.g., city of residence, occupational sector, economic status, personal preferences]."
  - State the convergence goal: "Now our primary goal was to systematize our research to track progress and identify a pivotal issue that, if addressed, could substantially enhance the overall well-being of [USER]."

- **The HMW callout:** Round 1's HMW question reproduced verbatim in a callout/quote bubble with oversized quotation marks, identical visual treatment to its appearance in Round 1. This is the anchor — every section that follows must trace back to this question.

**Voice:** First-person plural, methodological, slightly more formal than Rounds 1 and 2 (the team is making a decision now, not just exploring).

### Page 1, Section 2: Problem Scoring

**Function:** Quantify team consensus on which candidate problems are most worth pursuing.

**Length:** 1–2 sentences of framing + a multi-team-member radar chart + 1 closing sentence naming the top 3.

**Structure:**
- **Framing sentence:** "We narrowed down upon [N] final problems that we scored on the basis of **[CRITERIA, bolded as a list — typically 6–7 criteria]**."

- **The radar/spider chart:** A multi-axis polar chart where:
  - Each axis = one candidate problem (typically 6–8 candidates)
  - Each criterion is scored by each team member (this is the unusual move — INDIVIDUAL scoring, not team-aggregated)
  - Each team member's scores are plotted as an overlaid polygon (different colors per member)
  - The chart visually shows agreement (overlapping polygons) and divergence (where one member's polygon extends further)

- **Closing sentence:** "Through the scores we further arrived upon **[N typically = 3] major problems** of **[BOLDED PROBLEM 1, BOLDED PROBLEM 2, BOLDED PROBLEM 3]**."

**The 7 default scoring criteria** (use these unless the team has a project-specific set):
1. **Feasibility** — can a small team realistically address this in the available time and resource?
2. **Excitement** — does the team genuinely want to work on it?
3. **Scalability** — can a solution serve many users beyond a pilot?
4. **Business Viability** — is there a sustainable revenue or funding model?
5. **Impact** — how meaningfully does solving this improve user well-being?
6. **Sustainability** — does the solution maintain its value over time, or decay?
7. **Interconnectivity** — does solving this problem also alleviate other connected problems?

**Critical pattern:** the radar chart shows INDIVIDUAL team member scores, not team averages. This communicates that the team scored independently before discussing, which is a stronger consensus signal than groupthink-averaged numbers. If the team only has aggregate scores, the radar chart's value is reduced — encourage individual scoring before drafting.

**Candidate problems should come from Round 2's problem mapping.** Pull the most prominent branches or sub-issues from Round 2 — typically 6–8 candidate problems that survived as "things worth considering."

### Page 1, Section 3: Narrowing Down

**Function:** Explicitly eliminate the rejected candidates with structured reasoning, then name the chosen problem with positive justification. Close with a pull quote that anchors the emotional case.

**Length:** 3 short paragraphs (one per problem treated) + 1 pull quote.

**Structure:**
- **Three problem blocks** (typically: 2 rejected + 1 chosen), each:
  - Status icon: ❌ for rejected, ✅ for chosen
  - Problem name as heading
  - 2–4 sentence reasoning paragraph with bolded key phrases

- **Rejection reasoning** must use one or more of these structured arguments. Bolded phrases come from this vocabulary:
  - **Scope mismatch with the user** — "is not exclusive to [USER]," "extends beyond [USER]"
  - **Specialization required beyond team capability** — "requires specialized knowledge and skills that cannot be acquired in a short period of time"
  - **Low interconnectivity** — "may yield a limited impact as it is not closely interlinked with other challenges"
  - **Existing solutions adequate** — "is already well-addressed by [SERVICE]" (use sparingly — only if true)
  - **High stigma / sensitivity** — "is a multifaceted [TYPE OF ISSUE] with stigma and limited awareness" (acknowledges difficulty without dismissing the problem's importance)

- **Acceptance reasoning** uses the inverse structure with positive bolded phrases:
  - **Tight user fit** — "directly impacts their professional obligations," "is the primary apprehension of [USER]"
  - **High interconnectivity** — "is closely interlinked with a number of many other smaller problems"
  - **Under-addressed** — "yet this issue remains largely neglected" (the *yet* is doing the work here)

- **Pull quote** with dual-identity attribution (e.g., "Payal Sinha, A Developer & A Mother"). The quote should be specific to the chosen problem, not a general user quote. It anchors the emotional reason this problem matters.

**Important:** the rejection reasoning is not dismissive of the rejected problems. It does not say "these problems are unimportant." It says "these problems are real, but they don't fit *this team's project scope for this round*." Phrases like "Working on this problem requires specialized knowledge and skills that cannot be acquired in a short period of time" acknowledge legitimacy while making a resource-realism argument. Tone matters here — the team is being intellectually honest, not gatekeeping.

### Page 2: Ecosystem Map (of the chosen problem area)

**Function:** A full-page multi-layer ecosystem map of the chosen problem. This is the most visually complex artifact across all three rounds.

**Length:** Full page. One large radial diagram + a 1–2 sentence caption + a legend.

**Caption structure:**
"The ecosystem map represents the **various themes** under [CHOSEN PROBLEM] while highlighting **the needs of the user, the major stakeholders, the touchpoints involved and the interlinkages** between them. **Concentric circles** are used to indicate **the impact of each theme and need on the user**, i.e., the closer the data, higher the impact."

The bolded phrases name the visual grammar — the caption teaches the reader how to read the diagram.

**Visual grammar (legend specifies all of these):**

1. **Center node** — the affected user(s). For the original: Mother + Child (the affected dyad). For other problems: the user + their primary linked party (e.g., elderly + adult child, student + parent).

2. **5–7 themes radiating outward** — categories that organize the problem space around the user. Themes should be domain-spanning nouns, not actions. Examples for the original: Care Facilities, Physical Health, Mental Health, Development, Transport, Nutrition. Plus optionally a cross-cutting **Government** or **Policy** theme on the side.

3. **Needs** (rendered as orange/peach dots with labels) — the user's specific requirements within each theme. **Positioned at varying distances from the center** — closer dots = higher impact needs. This spatial encoding does real work: a need placed close to the center is saying "this matters most." Each theme has 5–12 needs.

4. **Touchpoints** (rendered as coral squares with labels) — the specific interaction points or artifacts the user encounters within each theme. Examples: "Daycare Websites," "Diet Charts," "Health Checkups," "Navigation Apps," "Therapy." Each theme has 1–5 touchpoints.

5. **Stakeholders** (rendered as text labels branching off via thin lines from each theme) — the people, organizations, or institutions involved in each theme. Often sub-categorized (Public/Private/Government). Examples: "Daycares/Crèches → Anganwadis (Public), Workplace (Private), Private." Each theme has 2–8 stakeholders.

6. **Inter-theme linkages** — **thick coral lines** indicating strong connections between themes, **thin lines** indicating weak connections. Not every theme links to every other theme — only the genuine connections show. These linkages are the most important argumentative element: they argue that the chosen problem is *interconnected*, which was the original acceptance reason on Page 1.

7. **Concentric ring boundaries** (dotted) labeling "Level of Impact" — typically 2 nested dotted rings dividing high-impact / medium-impact / lower-impact zones.

**The map's design philosophy:** density is the argument. The page should look slightly overwhelming. It says "we have mapped every dimension of this problem." A clean, minimal version of this page would actually fail — it would suggest the team hasn't gone deep enough.

**Drawing from real research:** every theme, need, touchpoint, and stakeholder should trace back to either Round 2's problem mapping, an interview, a field observation, or a desk-research finding. Do not invent elements to fill the diagram.

### Page 3, Section 1: Pain Points

**Function:** Identify specific failure modes in the existing solution landscape for the chosen problem.

**Length:** 15+ short pain-point labels arranged around a central icon + 2 pull quotes.

**Structure:**
- **Opening sentence:** "After Ecosystem Mapping, we uncovered pain-points in the existing [PROBLEM AREA] system."
- **A central icon** depicting the existing service category (e.g., a daycare building for childcare, an elder-care centre for elderly services, a public transport vehicle for transportation problems).
- **15+ pain points radiating out from the icon as text labels** — each 3–7 words, very specific. Examples: "Inability to build trust," "Homely environment missing," "Lack of reliable transport service," "Infections spread easily," "No standardized regulations by the government," "Incorrect Staff-to-child ratio."
- **Bridging sentence:** "This is what some of the mothers had to say while discussing their personal views and experiences with the [SERVICE]."
- **2 pull quotes**, both with dual-identity attribution. These quotes should be *specific to the existing service experience*, not general user-life quotes. They're empirical evidence for the pain points listed.

**Important pattern:** the pain points are pain points OF THE EXISTING SYSTEM, not pain points OF THE USER in general. The icon makes this clear — the daycare building is the source of the problems. This is a subtle but important framing move: the team is saying "the problem is the system, not the user."

This is distinct from Round 2's problem mapping. Round 2 mapped problems in the user's life broadly. Round 3's pain points map failure modes of the existing service category the team is preparing to redesign.

### Page 3, Section 2: Indian/Regional Scenario (revisited)

**Function:** Re-contextualize the chosen problem within the cultural and infrastructural reality of the geography. Each round revisits this section through a new lens.

**Length:** 2–3 short paragraphs.

**Structure:**
- **Paragraph 1:** Name the cultural perception of the chosen problem in your geography. The pattern: "In [GEOGRAPHY], [CULTURAL CONTEXT], but [CHOSEN PROBLEM AREA] is often viewed [NEGATIVELY/PROBLEMATICALLY] and **[CULTURAL ATTRIBUTION]**." For the original: "In India, joint families are common, but daycare is often viewed negatively and **childcare is primarily seen as the mother's responsibility**."

- **Paragraph 2:** A specific perception that needs unlearning. For the original: "Many people still view daycare as a way to **avoid parenting duties**, especially for mothers, making it crucial to educate ourselves, our children and family members about the it's benefits." This is the team naming a stigma they will work against.

- **Paragraph 3:** The infrastructure gap that compounds the cultural issue. For the original: "In many regions, especially the rural areas with limited formal childcare options, **families rely on informal arrangements** with neighbors or relatives. This presents challenges for working parents in need of reliable and affordable childcare." This widens the picture to acknowledge that the formal solution landscape isn't universal.

**How this differs from Rounds 1 and 2:** Round 1 named the broad national scenario. Round 2 added a filtration funnel and cultural deep-dive. Round 3 zooms in to the *chosen problem's specific cultural treatment* — narrower than ever before.

### Page 3, Section 3: Setbacks of [Existing Service]

**Function:** Deepen Round 2's services audit with quantified evidence and specific failure modes. The pros are gone — only specific failures remain.

**Length:** Brief framing + 4 icon-labeled failure modes + a quantified statistic + 2–3 short paragraphs on additional setbacks.

**Structure:**
- **Service framing sentence:** "[SERVICE NAME], which is a type of [WHAT IT IS] in [GEOGRAPHY], has faced a range of problems in recent years." Keep it factual — no editorializing.

- **4 specific failure modes** rendered as **icon + short label pairs** arranged in a row. Each failure mode is 2–4 words. Examples from the original: "Low Space," "Shortage of Caretakers," "Underqualified Staff," "Improper Hygiene."

- **A specific concerns paragraph** naming concrete operational failures with bolded key phrases: "Concerns arise over meeting children's dietary requirements with **limited food options**, **early closure times (2 pm)** inconveniencing working parents, and **inadequate supervision** posing risks to children's safety and well-being."

- **One quantified statistic** with the visual treatment of a hero stat: "Only **54.5%** enrolled children attended regularly across 21 AWCs." Sourced to a named report (e.g., "Report on Evaluation of the Performance of Anganwadi"). The stat should be a *failure metric* — attendance, completion, satisfaction, dropout, etc. — not a generic prevalence number.

- **Two closing observations:**
  - One on systemic enrollment issues: "It was seen that some parents only enroll their children in these institutions because of **government regulations**." (The implication: enrollment numbers overstate actual engagement.)
  - One on worker conditions: "**Overworked employees** and **excessive record managing** were also major setbacks to the system."

**The progression of services audit across rounds:**
- Round 2: balanced pros/cons table — "this service exists, here are its strengths and limitations"
- Round 3: failure-focused — "this service is specifically failing in these quantified ways"

If your Round 3 setbacks section is just a re-listing of Round 2's cons, you haven't deepened — you've recycled.

### Page 4, Section 1: Impact

**Function:** Make the social impact case for solving the chosen problem. Show that the problem's solution ripples outward across multiple beneficiary groups.

**Length:** 5 ripple-effect statements with icons, each a 2–3 sentence paragraph.

**Structure — the 5 layers of impact ripple:**

The 5 impacts should span an expanding ripple from individual to society. Use this ordering as a default and adapt to your chosen problem:

1. **Direct primary beneficiary impact** — what improves for the most directly affected person. For the original: child's cognitive and social growth.
2. **User impact (your HMW user)** — what improves for the user named in the HMW. For the original: working mothers' reduced stress, productivity, career advancement.
3. **Family / household impact** — what improves for the user's household. For the original: parents returning to work → economic growth + reduced poverty.
4. **Adjacent affected parties** — who else benefits indirectly. For the original: older children freed from caregiving responsibilities → education + workforce.
5. **Societal / structural impact** — what changes at the systemic level. For the original: gender equality, workforce participation, pay gap narrowing.

**Each impact statement** has the same structure: a 2–3 sentence paragraph with the key impact phrase in **bold**. Examples:
- "Good childcare supports kids' **cognitive and social growth** in a caring setting, boosting their maturity and independence for later life."
- "It **enables parents to return to work**, participate more, earn more, and rely less on governmental aid, leading to **increased economic growth, and reduced poverty**."

**Each impact gets a custom line-icon** depicting the beneficiary group (child, parent figure, family, gender symbols, etc.).

The expanding-ripple structure is the same pattern Round 1 used for the original HMW's expected impacts. Round 3 expands it from 4 to 5 ripples and grounds each in the *specific* chosen problem area, with more concrete causal language.

### Page 4, Section 2: Business Viability

**Function:** Make the commercial / market case for solving the chosen problem. Show the team has thought about sustainability, not just impact.

**Length:** 3 short paragraphs with icons + 2 hard market data points + source citation.

**Structure:**
- **3 business viability arguments**, each as a 1–2 sentence paragraph with a custom icon and bolded key phrases. Pattern:
  1. **Quality gap = innovation opportunity** — "The current state of [SERVICE CATEGORY] in [GEOGRAPHY] is **lacking in quality**, creating a unique opportunity for innovation within the industry."
  2. **Demand evidenced by willingness to pay** — "The **demand for [SERVICE] is high**, as evidenced by the willingness of [USER] to pay for such services."
  3. **Demographic / structural tailwind** — "[GEOGRAPHY]'s **population growth and urbanization** have led to more nuclear families, and with more [TREND], **accessible [SERVICE] are becoming crucial** as **[OLD SUPPORT STRUCTURE] are no longer available**."

- **2 hard market data points**, each rendered as an icon + large number + label:
  - **Market Size** — typically with a current-year value and a projected future-year value (e.g., "2022: US$ 3.8 Billion → 2028: US$ 7.3 Billion")
  - **Market Growth Rate** — a CAGR figure with a year range (e.g., "11.2% during 2023–2028")

- **A named market research source** (e.g., "Source: Report by IMARC Group"). Use real, retrievable market research reports — IMARC, Statista, Mordor Intelligence, Grand View Research, Frost & Sullivan, Euromonitor, McKinsey market reports. Do not fabricate market sizes.

**This is a new framing tone for the case study series.** Rounds 1 and 2 were primarily empathetic. Round 3 introduces *commercial* framing because the team is preparing for ideation, and the solutions will need to be viable, not just well-intentioned. The voice shifts slightly toward operator-pragmatism here without losing the empathetic foundation.

**If the chosen problem doesn't have an obvious commercial market** (e.g., government policy interventions, public-goods problems), reframe the business viability section as "Funding Viability" or "Sustainability Pathway" — naming who pays for or sustains the intervention (government budgets, philanthropic capital, cross-subsidy from related services). Don't force a market frame if it isn't natural.

### Page 4, Section 3: How Might We? (refined)

**Function:** Refine the broad Round 1 HMW into 3 sharper sub-HMW questions that each represent a different angle of solution space.

**Length:** 3 short HMW questions, each in a callout-bullet treatment.

**Structure:**
- Each sub-HMW must follow the standard HMW formula: soft verb + scoped user/aspect + aspirational outcome.
- The 3 sub-HMWs together should span **different angles of solution space** — not be synonyms. Use this default angle-trio:

  **Angle 1 — Well-being / holistic care:** "How might we prioritise the [PHYSICAL/MENTAL] well-being of [USER PAIR] while [ALSO ENSURING/INCLUDING ANOTHER CARE DIMENSION]?"

  **Angle 2 — Developmental / social / cultural:** "How might we help provide [PRIMARY BENEFICIARY] with [DEVELOPMENTAL OUTCOME] in [CONTEXTUAL CHALLENGE]?"

  **Angle 3 — Operational / service-reliability:** "How might we help [USER] find a [QUALITY DESCRIPTORS] [SERVICE] which [ENSURES SAFETY/QUALITY] while [ACCOMMODATING CONSTRAINTS]?"

  Each angle gestures toward a different *type* of solution: Angle 1 → care-service design; Angle 2 → educational/social/community design; Angle 3 → service-operations design.

- The 3 sub-HMWs together should be **non-overlapping**. Test: if you could answer Sub-HMW A in a way that automatically answers Sub-HMW B, the two aren't sufficiently distinct. Rewrite.

- The 3 sub-HMWs should each be **a valid stand-alone HMW** that the team could ideate against in Round 4. None should require "and also do everything from the other two" to be meaningful.

**The structural argument of having 3 sub-HMWs:** the team is signaling that they intend to ideate across multiple solution-space directions in Round 4, not commit to a single solution angle prematurely.

### Page 4, Section 4: Need Statement

**Function:** State a formal, single-sentence need statement in the classic **User + Need + Insight** ("so that") format. This is the artifact that will guide all of Round 4's ideation.

**Length:** 1 sentence in a callout/quote bubble with oversized quotation marks. Plus the team credit line below.

**Structure — the User + Need + Insight formula:**

> **[USER]** need **[SPECIFIC NEED — what kind of service/intervention/support]** so that **[INSIGHT — the deeper outcome they're really after]**.

**Example from the original:**
> "**Employed mothers** need **a reliable service that priorities mother-child well-being and nutrition while providing children with consistent interaction & connection** so that they can **feel safe about their child and thrive in their career**."

**Construction rules:**
- **User** — same as Round 1's HMW user (the scoped life-phase user, not a demographic).
- **Need** — specific enough to constrain solution space but not so specific it becomes a solution. The need should name the *qualities* of the desired service (e.g., "reliable," "prioritises mother-child well-being and nutrition," "provides consistent interaction"), not the *form* (e.g., "an app" or "a community center"). Form is for Round 4.
- **Insight (the "so that" clause)** — the deeper outcome that explains WHY the user wants the need met. This is the most important part — it's the success criterion for the eventual solution. Common patterns: "so that they can [feel X about Y] and [achieve Z]."

**The two-part insight pattern** is important. For the original: "so that they can **feel safe about their child** AND **thrive in their career**." One clause addresses the *anxiety* the user wants relieved; the other addresses the *aspiration* they want enabled. This dual-part insight forces the eventual solution to address both an emotional and a functional outcome.

**Team credit line** appears at the bottom of Page 4, in italic or muted styling, matching Round 1 and Round 2 conventions: "Team [NAME]: [Member 1], [Member 2], [Member 3], [Member 4]."

## Voice and tone

Follow all voice and tone rules from `discovery-brief-case-study` and `empathy-deepening-brief-case-study`. First-person plural, hedged claims, bolded key phrases (not whole sentences), no AI prose tells, empathetic but not saccharine.

**Round 3-specific voice rules:**

- **Decisiveness without arrogance.** This is the round where the team commits. The voice should sound *resolved* rather than *exploring*. But the rejection reasoning must remain respectful — "this problem is real and important, but doesn't fit *our project's scope*" is the tone. Never dismissive ("this problem isn't worth solving").

- **Quantitative-friendly tone.** Round 3 introduces market data and quantified failure metrics. Embrace numbers without abandoning the empathetic frame. A statistic like "Only 54.5% enrolled children attended regularly" should be presented matter-of-factly, with the human consequence implied but not over-narrated.

- **Operator vocabulary appears.** Words like "feasibility," "scalability," "business viability," "interconnectivity" — they're acceptable in Round 3 because the team is doing operator work (selecting an opportunity, justifying a market). But still avoid filler buzzwords like "leverage," "synergy," "holistic," "comprehensive."

- **No solution-leakage, still.** Even on Page 4 with the refined HMWs and need statement, do not name specific solutions. The need statement should name *qualities* of the desired service, not its *form*. "Reliable service that prioritises X" — fine. "Mobile app for daycare booking" — not yet.

- **Italicize sparingly.** Round 3 doesn't use italics as a primary emphasis tool (Round 2's experience map did). Stick to bold for key concepts. If italicizing, reserve for service or scheme names with local-language equivalents (e.g., *Anganwadi*).

## Visual design language

Follow all visual design rules from the prior round skills. Same warm coral / dusty rose / cream palette, same custom line-art iconography, same wavy section dividers, same sans-serif typography.

**Round 3-specific visual elements:**

- **Multi-team-member radar chart (Page 1):** A polar/spider chart with 6–8 axes (one per candidate problem). Overlapping polygons, one per team member, each in a distinct soft color. Team-member names in a small legend with color-dot markers. The polygons should be partially transparent so overlap is visible.

- **HMW callout (Page 1):** The Round 1 HMW reproduced verbatim in a soft-background callout box with large quotation marks ('99-style') in the top-left and bottom-right corners. Identical visual treatment to its appearance in Round 1.

- **Status icons (Page 1, Narrowing Down):** A red ❌ (or stylized X in a circle) for rejected problems, a green ✅ (or stylized checkmark in a circle) for the chosen problem. Both rendered in the line-icon style consistent with the rest of the document.

- **Multi-layer ecosystem map (Page 2):** The most complex artifact across all rounds. A radial diagram with:
  - Central node (user + linked party)
  - 5–7 themes radiating outward as labeled icons
  - Needs as small dots with text labels at varying radial distances (closer = higher impact)
  - Touchpoints as coral squares with text labels positioned within each theme zone
  - Stakeholders as text labels branching off via thin lines with optional sub-categorization (Public/Private/Government)
  - Inter-theme linkages as thick (strong) or thin (weak) curved coral lines
  - Two or three concentric dotted ring boundaries indicating "Level of Impact"
  - A legend on one side explaining all 6 visual elements (Needs, Stakeholders, Strongly Linked, Weakly Linked, Stakeholder Linkage, Themes, Touchpoints, Level of Impact)

- **Painpoints-around-icon (Page 3):** A large central icon depicting the existing service category (e.g., a daycare building) with 15+ pain-point labels radiating outward via thin lines. Each label is plain text (no bullet). Labels distributed evenly around the icon.

- **Anganwadi-style failure icons (Page 3):** A row of 4 icon-label pairs depicting specific failure modes. Each icon is custom line-art, each label is 2–4 words below the icon. Consistent visual weight across all four.

- **Hero failure stat (Page 3):** A large numeric callout (e.g., "Only **54.5%**") with a small explanatory caption ("enrolled children attended regularly across 21 AWCs") and source attribution. Visual treatment matches the Round 1 and Round 2 hero stats but in a slightly muted tone since this is a failure metric.

- **Impact icons (Page 4):** 5 ripple-effect impact statements, each with a custom icon depicting the beneficiary group (child, parents, working mother, siblings, gender equality symbol). Arranged in a vertical zigzag layout (alternating left-right) so each impact + icon pairing gets its own visual rhythm.

- **Market data callouts (Page 4):** Two icon-label-number callouts for Market Size and Market Growth Rate. Numbers large and prominent, sourced beneath.

- **Sub-HMW bullets (Page 4):** 3 sub-HMW questions, each prefixed with a small coral dot/bullet, in a slightly larger font than body text. Clean, scannable.

- **Need Statement callout (Page 4):** The need statement in a soft-background callout box with oversized quotation marks (matching the Round 1 HMW callout on Page 1, creating visual bookending across the brief).

## Source and evidence standards

Follow all source standards from the prior skills. Real, named, retrievable sources. No fabrication.

**Round 3-specific sourcing:**

- **Problem scoring should be sourced to the team's own process.** Cite "Source: Problem Scoring" at the bottom of Page 1's scoring section to indicate the data is internal to the team's process, not external. Do not invent external citations for what was an internal exercise.

- **Failure statistics must be from real reports.** The "54.5% enrolled children attended regularly" stat needs an actual government or NGO evaluation report behind it. Search for real performance evaluations of the existing service before drafting this section.

- **Market data must be from real market research firms.** IMARC, Statista, Mordor Intelligence, Grand View Research, Frost & Sullivan, Euromonitor, McKinsey, BCG, Bain market reports. Do not fabricate market sizes or CAGRs. If the user provides market data without a source, ask where it came from before including it.

- **Pull quotes must be real interview quotes.** Round 3 introduces 3 new dual-identity pull quotes (Payal Sinha on Page 1, Shreya Singh and Divya Gupta on Page 3). Each must come from real second-wave interviews. Do not synthesize quotes "in the spirit of" what users said.

- **Sources for the ecosystem map.** Themes, needs, touchpoints, and stakeholders all should trace back to Round 2's problem mapping or to subsequent interviews. Inter-theme linkages should be defensible — if asked "why is Mental Health strongly linked to Care Facilities," the team should have an answer from their research.

## Common failure modes — read before producing the final output

1. **No HMW callout on Page 1.** The Round 1 HMW question doesn't appear, or appears only in the body text. *Fix:* the HMW belongs in a prominent callout bubble with oversized quotation marks. It anchors the entire round.

2. **Problem scoring uses team averages instead of individual scores.** The radar chart shows one polygon (team average) rather than overlapping polygons (per team member). *Fix:* go back to individual team-member scoring. The chart's value is showing both consensus and divergence.

3. **Rejection reasoning is dismissive of the rejected problems.** Sentences like "Household chores aren't really a problem worth solving" or "PPD is too small to matter." *Fix:* the rejection is *for-this-team-this-round*, not *forever*. Use scope-mismatch language ("not exclusive to [USER]," "extends beyond [USER]") and resource-realism language ("requires specialized knowledge cannot be acquired in a short period").

4. **Chosen problem doesn't appear in Round 2's problem mapping.** The team is committing to a problem they hadn't researched. *Fix:* either go back to Round 2 and expand the problem mapping to include the new focus, or pick a chosen problem that's already in Round 2's mind-map.

5. **Ecosystem map is just a list of stakeholders.** The map looks like Round 2's stakeholder map with a new title — no themes, no needs, no touchpoints, no inter-theme linkages. *Fix:* the Round 3 ecosystem map has 6+ distinct visual elements (themes, needs, stakeholders, touchpoints, linkages, impact rings). If 4+ of these are missing, the page fails.

6. **No inter-theme linkages on the ecosystem map.** Themes sit in isolation. *Fix:* inter-theme linkages are the argumentative element — they justify the "interconnected" rationale used to pick this problem. Add at least 4–6 inter-theme connections with thick (strong) or thin (weak) line weights.

7. **Pain points are vague or repeat Round 2's problem space.** "Stress," "burnout," "lack of support." *Fix:* pain points should be specific to the existing service category — "Lack of Vacancy," "No Certifications or trainings available," "Open only for regular working hours," "Incorrect Staff-to-child ratio." Each should be a thing a team member could point to in a real service.

8. **Indian/Regional Scenario rehashes earlier rounds.** Same content as Round 1 or Round 2. *Fix:* this section in Round 3 must be specific to the *chosen problem's cultural treatment* — narrower than ever before. If your Round 3 scenario could be cut-and-pasted from Round 2, you haven't zoomed in.

9. **Setbacks section is just Round 2's pros/cons cons-list.** *Fix:* Round 3's setbacks should go deeper than Round 2 — with quantified failure metrics, specific operational failures, and worker-condition observations. The progression: Round 2 = balanced audit; Round 3 = quantified failures.

10. **Impact statements are platitudes.** "It will help families be happier." "It will make society better." *Fix:* each impact should have a specific causal chain — what concretely improves, and through what mechanism. Use the 5-ripple ordering (primary beneficiary → user → family → adjacent → society) to force specificity.

11. **Business viability has no real market data.** *Fix:* find an actual market research report. If the chosen problem genuinely has no market (e.g., it's a public-goods or policy problem), reframe the section as "Funding Viability" — naming who pays for or sustains the intervention.

12. **The 3 sub-HMWs are synonyms.** They all say the same thing in different words. *Fix:* each sub-HMW must gesture toward a *different solution-space angle* — well-being/holistic care, developmental/social, operational/service-reliability. Test: if answering one sub-HMW automatically answers another, they're not distinct.

13. **The Need Statement names a solution form.** "Mothers need an app that…" *Fix:* the need statement names *qualities* of the desired service, not its form. Form is for Round 4.

14. **The Need Statement's "so that" clause is missing or vague.** *Fix:* the "so that" clause is the insight — the deeper outcome the user really wants. It should typically be a two-part outcome (anxiety relieved + aspiration enabled). "So that they can feel safe about their child AND thrive in their career."

15. **Solution-leakage.** Sentences like "Our app will…" or "The platform we're building…" appear anywhere. *Fix:* Round 3 is still pre-ideation. No solutions yet.

## Worked mini-example (adapted to a new problem statement)

Continuing the elderly-loneliness example from the prior skills' worked examples. **Illustrative only.**

**Round 1 HMW (carryover):** "How might we help elderly individuals living alone in urban India sustain meaningful daily connection?"

**Round 3 Page 1 — Introduction + HMW Callout + Problem Scoring + Narrowing Down:**

Re-state the Round 1 HMW in callout. Intro paragraph names dimensions of variation: financial status, family proximity, mobility, technology fluency.

Candidate problems from Round 2's problem mapping (7 candidates):
- Loss of social anchor post-spouse-loss
- Health emergencies (no immediate response system)
- Digital divide (cannot use video calling)
- Mobility-related isolation
- Daily companionship gap
- Loss of identity/purpose post-retirement
- Financial precarity for informal-sector retirees

Radar chart with overlapping polygons for each of 4 team members across 7 criteria. Top 3 emerge: Daily companionship gap, Health emergencies, Loss of identity/purpose.

Narrow down:
- ❌ Health emergencies — "requires specialized **medical infrastructure** that extends beyond a design intervention; better addressed by **government policy and telemedicine**"
- ❌ Loss of identity/purpose post-retirement — "is **highly individual** and varies significantly across personality, vocation, and worldview; **may yield a limited impact** at the service-design level"
- ✅ Daily companionship gap — "is **the primary apprehension** of elderly individuals; **closely interlinked** with mental health, mobility, cultural connection, and family relationships; yet **remains largely underserved** by formal services"

Pull quote from a real interview: "I have lived alone for eleven years since my wife passed. I have children abroad, but it is the everyday — the morning tea, the evening news — that I miss the most." — Mr. Krishnamurthy, A Retired Bureaucrat & A Widower.

**Round 3 Page 2 — Ecosystem Map of Daily Companionship:**

Center: Elderly Individual.
Themes: Social Connection, Mental Wellness, Cultural / Spiritual Practice, Daily Routines, Physical Activity, Technology Bridge, Government (cross-cutting).
Needs (positioned by impact distance): Daily presence, Trusted listener, Shared meals, Familiar voices, Spiritual community, Routine anchors, etc.
Touchpoints: Phone calls, Religious gatherings, Newspaper, TV, Walking groups, Day care centres, Senior community apps.
Stakeholders: Adult children, Domestic help, Religious community, Neighbors, Day care centres (Public/Private/NGO), Healthcare workers, Local government, Senior advocacy NGOs.
Inter-theme linkages: Strong link between Social Connection ↔ Mental Wellness; Daily Routines ↔ Physical Activity; Cultural Practice ↔ Social Connection.

**Round 3 Page 3 — Pain Points + Indian Scenario + Setbacks of Day Care Centres for Elderly:**

Pain points (15+) around an elder-care centre icon: "Limited operating hours," "Transport gap to/from centre," "Cultural mismatch in activities," "Stigma of being 'put away'," "Lack of personalized interaction," etc.

Two pull quotes (dual identity): "If I tell people I attend a senior centre, they will think my children have abandoned me. So I do not go." — Mrs. Padmaja, A Former Schoolteacher & A Widow. Plus another from a gerontologist.

Indian Scenario: "In India, **filial duty** is a cultural norm but **urban migration of adult children** has eroded its enforcement. Going to a senior centre is still seen as a **family failure**, making formal services socially expensive."

Setbacks of [Day Care Centres for Elderly — e.g., HelpAge India or analogous]:
- 4 failure icons: Limited Hours, Transport Gap, Cultural Mismatch, Underfunding
- Quantified stat: "Only X% of urban Indian elderly use any formal day-care service" (with real source)
- Worker conditions observation.

**Round 3 Page 4 — Impact + Business Viability + HMWs + Need Statement:**

Impact (5 ripples):
1. Elderly individual: reduced depression, better cognitive function, longer healthspan
2. Adult children: reduced caregiver guilt, freed bandwidth, sustained own careers
3. Healthcare system: lower emergency visits, better chronic disease management
4. Grandchildren / family: intergenerational connection, cultural transmission
5. Society: demographic-aging cost reduction, modelling of dignified aging

Business Viability:
- Quality gap in elder-care services in India
- Demand evidenced by willingness to pay among middle-class families with elders
- Demographic tailwind (India's elderly population projected to reach 19% by 2050)
- Market data: Indian elder-care market size (sourced from a real report).

3 refined HMWs:
- How might we help urban elderly sustain **trusted daily peer connection** while respecting their dignity?
- How might we help urban elderly access **cultural and spiritual community** without family-failure stigma?
- How might we help adult children of urban elderly **sustain meaningful long-distance presence** despite geographic separation?

Need Statement: "**Urban Indian elderly living alone** need **a dignified, culturally-rooted form of daily companionship and check-in** so that they can **feel anchored to a community** and **age with autonomy rather than abandonment**."

## Scoring Benchmark

Before delivering any Round 3 brief, score it on the four dimensions below. The first is **lower-is-better**. The other three are **higher-is-better**. Each maps to a specific cluster of Round 3 failure modes.

| Dimension | What It Measures | Target |
|-----------|-----------------|--------|
| **AI-Likeness** | Generic AI prose, filler phrases, melodrama, missing nuance moves, third-person drift, corporate jargon, solution-leakage. Voice should match Rounds 1 and 2 exactly, with the slight Round 3 shift toward operator-pragmatism without losing empathy. | 1–3 |
| **Convergence Rigor** | Does Page 1 anchor to the Round 1 HMW via a callout? Is the problem scoring quantified by individual team members (not just team averages)? Are the rejection arguments structured (scope-mismatch / specialization / interconnectivity) rather than dismissive? Does the chosen problem appear in Round 2's problem mapping? | 8–10 |
| **Theme-Ecosystem Depth** | Does the ecosystem map have 6+ distinct visual elements (themes, needs, touchpoints, stakeholders, inter-theme linkages, impact rings)? Are needs positioned by impact distance from the center? Are 4+ inter-theme linkages shown with strong/weak distinction? Are pain points specific to the existing service category and orbiting a central service icon? Does the Setbacks section deepen Round 2's audit with quantified failure metrics? | 8–10 |
| **Refinement Sharpness** | Do the 5 impact statements ripple from primary beneficiary to society? Is the business viability section grounded in real market data (or honestly reframed as "Funding Viability" if no market exists)? Are the 3 sub-HMWs at genuinely different solution-space angles (well-being / developmental / operational)? Does the Need Statement follow the User + Need + Insight ("so that") format with a two-part outcome? Does it name qualities, not solution forms? | 8–10 |

### What each dimension looks like at low vs. high scores

**AI-Likeness (lower is better)**
- *1–3 (target):* Reads like the same team that wrote Rounds 1 and 2. First-person plural. Decisive but not dismissive. Rejection language uses scope-mismatch and resource-realism, not "this problem isn't worth solving." Operator vocabulary (feasibility, viability, scalability) used precisely, not as filler. No solution-leakage even on Page 4.
- *7–10 (fail):* Generic, corporate, or melodramatic. Rejection reasoning is dismissive or strawman. Operator words become filler. Solution names appear ("our app," "the platform").

**Convergence Rigor (higher is better)**
- *8–10 (target):* HMW callout present and prominently treated. Radar chart shows individual team-member polygons. 2–3 problems explicitly rejected with structured arguments. Chosen problem traces directly back to Round 2's problem mapping. Pull quote on Page 1 emotionally anchors the choice.
- *1–4 (fail):* No HMW callout. Radar chart shows team-aggregated scores only. Rejection reasoning is brief or hand-wavy ("we just felt drawn to this"). Chosen problem is new to the project — not in Round 2's research.

**Theme-Ecosystem Depth (higher is better)**
- *8–10 (target):* Ecosystem map shows 5+ themes with needs (positioned by impact), touchpoints, stakeholders, and 4+ inter-theme linkages. Legend present and teaches the visual grammar. Pain points are 15+ items, specific to the existing service category, orbiting a service-category icon. Setbacks include quantified failure metrics from real sources.
- *1–4 (fail):* Ecosystem map looks like Round 2's stakeholder map with a new title. No inter-theme linkages. Pain points are vague life-issues, not service-failures. Setbacks rehash Round 2's audit without new data.

**Refinement Sharpness (higher is better)**
- *8–10 (target):* 5 impact statements span individual → society. Business viability cites real market data with a named research firm. 3 sub-HMWs occupy distinguishably different solution-space angles. Need Statement names qualities of the service (not its form), has a two-part "so that" outcome (anxiety relieved + aspiration enabled), and uses the same scoped user as Round 1.
- *1–4 (fail):* Impact statements are platitudes without causal chains. Market data missing or fabricated. 3 sub-HMWs are synonyms. Need Statement is vague, names a solution form, or has no "so that" clause.

### Scoring output format

```
## Self-Audit Scores

| Dimension | Score | Justification |
|-----------|-------|---------------|
| AI-Likeness | X/10 | [one sentence — name specific markers present or absent] |
| Convergence Rigor | X/10 | [one sentence — note HMW callout, scoring chart format, rejection argument quality] |
| Theme-Ecosystem Depth | X/10 | [one sentence — note ecosystem-map element completeness, painpoints specificity, setbacks depth] |
| Refinement Sharpness | X/10 | [one sentence — note impact ripple, viability data, sub-HMW angle differentiation, need-statement format] |
```

### Important diagnostic cross-checks

- **Convergence Rigor low AND Theme-Ecosystem Depth high** → The team did deep work on the chosen problem but didn't make their selection process visible. The reader sees impressive analysis but can't tell why this problem won over the others. Strengthen the scoring + rejection reasoning before delivery.
- **Theme-Ecosystem Depth high AND Refinement Sharpness low** → The team mapped the problem space thoroughly but didn't refine the question. The reader has a beautiful atlas but no sharper direction for Round 4. Tighten the sub-HMWs and Need Statement.
- **All dimensions high but the chosen problem doesn't match Round 2** → A coherence failure. The team is doing good Round 3 work, but on a problem they didn't actually research. Either redo Round 2 to include this focus, or change the focus to match what Round 2 covered.
- **Refinement Sharpness high AND Convergence Rigor low** → The team has sharp ideation prompts but the reader doesn't trust how they got there. The sub-HMWs look pulled-out-of-air rather than derived. Add scoring + rejection reasoning.

If any dimension scores below target after the first draft, revise that dimension before delivering.

## Operating procedure

When the user invokes this skill:

1. **Verify Rounds 1 and 2 exist.** Confirm both the Round 1 HMW and Round 2 outputs (especially the problem mapping) are available. If either is missing, suggest the user run the corresponding earlier skill first.

2. **Verify the chosen problem traces back to Round 2's problem mapping.** Ask the user where in Round 2 the chosen problem first appeared. If it doesn't appear, flag this incoherence before drafting.

3. **Verify inputs against the input checklist.** Read `inputs.md` (sibling file in this round folder) and confirm mandatory Round 3 inputs are provided. If anything mandatory is missing, ask before drafting. Note any high-value optional inputs that are missing and how their absence will limit output quality.

4. **Do real research.** Search the web for:
   - Real failure statistics on the existing-service category for Page 3 (e.g., government evaluation reports)
   - Real market data for the chosen problem area for Page 4 (e.g., IMARC, Statista, McKinsey reports)
   - Any additional sourcing needed for the regional scenario revisit

   Do not fabricate. If market data isn't findable, ask the user or honestly reframe Business Viability as Funding Viability.

5. **Plan the convergence arc.** Before drafting, walk through the 10 moves of the Converge → Commit → Refine arc (Anchor → Score → Eliminate → Choose → Map → Pain → Audit → Justify-social → Justify-commercial → Refine → Need-state) and verify each will be present.

6. **Draft section by section** following the section playbook above. For each section, output:
   - The prose / content
   - Required statistics with citations
   - A "Visual elements to design" callout describing what the user needs to design

7. **Audit against the 15 failure modes** before scoring.

8. **Self-score using the Scoring Benchmark.** If any dimension misses target, revise and re-score before delivering. Include the final scoring table in the output.

9. **Deliver as a single document** structured as the 4 pages, with clear page breaks and section headings, formatted in markdown unless the user requests a different output format.

10. **Offer next steps.** Ask whether the user wants:
   - A visual HTML/SVG mockup of any specific section (the multi-layer ecosystem map is especially worth mocking up given its complexity)
   - A second iteration on a specific dimension where the score missed target
   - Help drafting Round 4 (ideation / solution phase, which this skill does NOT cover)
